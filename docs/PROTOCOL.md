# Протокол / Protocol

AirMode contains original Kotlin implementations. Only public protocol descriptions were consulted; companion app source was not copied. **Fixtures and compilation do not qualify interoperability of expanded Apple/Sony hardware.** The user reported successful noise switching on Pixel10Pro CP41.260831.007.A3 / AirPods5 using0.1.0, with missing battery/popup. The subsequent0.1.1 diagnostic report supplied actual sanitized AirPods5 battery packets, model A3531/A3532 and modes1/2/3 on SDK37. The0.1.2 report now contains incoming mode4 after1807ms; acoustic qualification of every mode and independent battery accuracy remain incomplete.

## Native transport

Classic Bluetooth L2CAP PSM `0x1001`, never LE CoC or GATT. `Session` uses `ClassicTransport` to invoke `BluetoothDevice.createL2capSocket(int)` through the pinned Apache-2.0 dependency `org.lsposed.hiddenapibypass:hiddenapibypass:6.1`. This generic runtime bridge invokes only the socket factory: it sets no global exemptions, changes no system policy, requires no root/Xposed and grants no Bluetooth privileges. OEM implementation, runtime changes, pairing state and firmware can still prevent access. There is no vendor impersonation or OS-version assumption. Pixel 10 Pro / 11 Pro, current releases and beta builds use the same runtime capability gate; exact hardware/build compatibility needs physical qualification.

[Official Android 16 non-SDK flags](https://dl.google.com/developers/android/baklava/non-sdk/hiddenapi-flags.csv), linked by [Android compatibility documentation](https://developer.android.com/guide/app-compatibility/restrictions-non-sdk-interfaces), classify `createL2capSocket(I)` as `lo-prio,max-target-o`. The file was downloaded and its SHA-256 matched the official value `9102af02fe6ab68b92464bdff5e5b09f3bd62c65d1130aaf85d3296f17d38074`. For target SDK 36, ordinary reflection is therefore blocked by the published Android 16 list. That is why ordinary reflection was replaced by the narrow invocation bridge; successful native factory tests must be recorded separately in `VERIFICATION.md`. They establish socket creation only, not a usable AirPods connection or working noise control. Current AOSP [BluetoothSocketSettings](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/framework/java/android/bluetooth/BluetoothSocketSettings.java) only supports RFCOMM and LE sockets, not classic L2CAP. Its [CTS test](https://android.googlesource.com/platform/cts/+/refs/heads/main/tests/tests/bluetooth/src/android/bluetooth/cts/BluetoothSocketSettingsTest.java) explicitly rejects `TYPE_L2CAP`. Physical Android 17/beta control compatibility remains unverified; neither OS upgrade nor successful APK installation establishes that control is accessible. AOSP `getMetadata` additionally requires privileged Bluetooth permission, so ordinary-app component metadata fallback can also be unavailable.

[AOSP BluetoothDevice](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/framework/java/android/bluetooth/BluetoothDevice.java) describes the classic constructor. [AOSP BluetoothSocket](https://android.googlesource.com/platform/packages/modules/Bluetooth/+/refs/heads/main/framework/java/android/bluetooth/BluetoothSocket.java) buffers incoming L2CAP SDUs. AirMode reads with the negotiated receive MTU so that a small application buffer cannot split a packet. Each SDU is parsed independently; truncated, overlong and unknown frames are ignored. There is no universal AAP frame length or unsafe scanning of arbitrary payload bytes for a header.

Connect and initialization expire after 10 seconds without a valid parsed report; the repository applies an additional6-second Apple /10-second Sony readiness deadline; cancellation closes the socket to unblock native I/O. The CONNECT_RSP validation follows [primary AAP reverse-engineering notes](https://gist.github.com/R00tKited/4fc75e67280768976476fc5c341c69f1): message type 1, service ID 4, then little-endian result at offsets 4–5. AirMode requires at least six bytes and result zero; nonzero results, including the observed `0x0085` refusal, are rejected. The remainder is not decoded; responses above a conservative 64-byte boundary are rejected. This is public protocol evidence, not a physical AirMode capture. [WOOT20 primary research](https://www.usenix.org/system/files/woot20-paper-heinze.pdf), Appendix A.2.1, describes the general AAP header but does not establish negotiation result semantics or supported firmware response sizes. A handshake acknowledgement alone does not set `Ready`. A valid metadata, battery or listening report must follow. Repository connection-generation checks isolate delayed events. Repository and transports require fresh confirmed identity and target membership in the model’s supported modes before physical noise writes.

## Public AAP definitions

Source: [AAP Definitions](https://github.com/librepods-org/librepods/blob/main/docs/AAP%20Definitions.md), a public protocol document describing AirPods Pro 2 firmware 7A305, **not proof for AirMode's supported generations**. Handshake begins `00 00 04 00`, differing from the PRD's ordinary-command prefix. Subscription sends both documented masks once after acknowledged handshake: `040004000f00fffffeff` and `040004000f00ffffffff`. The independent author of [Voltaic documents firmware-dependent battery delivery](https://github.com/jcfs/voltaic#airpods); no companion source was consulted. The user’s AirPods5 report now confirms22-byte battery reports are delivered and accepted. Listening reports contain the selected mode; writes cannot confirm it. 0.1.2 sends the documented14-byte `040004004d00ff00000000000000` capability declaration once per live, protocol-confirmed ANC session, only after explicit Adaptive selection. It precedes the ordered listening-mode write; it does not delay handshake subscriptions or establish mode success. Any0x002b response is logged as a capability response, never as mode4. The public document associates this mask with both Adaptive and CA during audio, and was captured on Pro2 rather than supportedAirPods5: it is a bounded compatibility trial, not a CA-neutrality or hardware qualification claim. No CA-setting write is sent. Different/rejected listening reports retain actual confirmed mode; the700ms retry applies;0.2.0 stops loading by1.5s and keeps neutral awaiting-confirmation until2.5s because the user’s actual mode4 reply arrived1807ms after writing. [Independent session notes](https://github.com/stuffz/airpods/blob/main/docs/l2cap.md) use a different0xd7 mask with unspecified bit semantics; AirMode does not infer an undocumented Adaptive-only bitmask.

The metadata example establishes `1d 00 02`, a little-endian body length at offsets 7–8 and `04 00` at 9–10. Total size is declared length plus 9. AirMode accepts this envelope only, decodes the first three NUL-terminated UTF-8 fields (name, model, manufacturer), and requires manufacturer `Apple Inc.`. It never searches serial or encrypted fields for a model. Unrecognized metadata variants leave the model unconfirmed.

Battery records validate count, exact length, unique components, markers and status. The component **table** says `04` left, `02` right, `08` case; the prose interpreting the example reverses left/right. AirMode follows the table, corroborated by [independent L2CAP research](https://github.com/stuffz/airpods/blob/main/docs/l2cap.md). Explicit unknown/disconnected components immediately withdraw current availability while retaining separately labelled last-known percentage and its original timestamp. Missing components do not withdraw availability. Each reading carries source and observation time; present nonstale AAP readings override lower-priority sources. Android metadata is explicitly last-known even at first process startup and has its own unchanged-value cache, so repeatedly reading it cannot acquire the timestamp of a different merged source. Unknown battery never means zero.

## BLE proximity

Sources: [researcher's proximity field guide](https://github.com/furiousMAC/continuity/blob/master/messages/proximity_pairing.md), [primary privacy research](https://petsymposium.org/2020/files/papers/issue1/popets-2020-0003.pdf), and [independent BLE capture guide](https://github.com/stuffz/airpods/blob/main/docs/ble.md).

`AdvertParser` accepts company `0x004C` payloads excluding company ID, exactly 27 bytes with prefix `07 19 01` and model-family suffix `20`. Offset 6 carries two battery nibbles; offset 7 carries case battery and charging flags. Values 0–10 mean 10% increments; 11–15 remain unknown. Status bit 5 identifies primary-left; low/high battery nibbles and charging bits 4/5 are primary/secondary and move together. The recent capture guide resolves advertiser order; older descriptions of a separate “flipped” bit conflict and are not used. Other prefix variants remain rejected. Recognized encrypted case formats are described below.

An advertisement is not model proof. Accept direct selected-pair addresses or private addresses resolved with a key from its fresh live Apple session; no RSSI/name attribution. Scan callbacks use the selected-pair epoch, independent of socket creation. Unknown layouts remain unavailable.

## Tests and privacy

`ProtocolTest` uses synthetic BLE and metadata fixtures constructed from field definitions, plus the public battery example and documented control bytes. They test parser expectations, malformed boundaries, UTF-8 rejection, all twelve model IDs, unknowns, advertiser-side swaps and mode mapping. Synthetic fixtures are not physical qualification. Tests additionally preserve the user-supplied AirPods5 packets48/61/100 followed by case status4 with00/FF, including changed component ordering. `BatteryTest` checks per-component freshness and stale-data boundaries. Runtime timestamps use `SystemClock.elapsedRealtime()`.

The decoder emits only name, model, battery, listening and ear-detection state; ear states are used for debug diagnosis and do not add auto-pause or gestures. Normal release Session has no raw packet logging, serial logging or network code. Debug diagnostics retain a bounded in-memory accepted battery-only packet body (12–22bytes), six-byte headers/type counts for other messages, BLE association counts and notification permission/channel state. Metadata bodies, names, serials and addresses are excluded. No automatic export, Logcat or disk persistence. Physical tests must record phone, OS build, beta status, AirPods model and firmware in `VERIFICATION.md` before hardware-ready claims.

Mode write rate is also enforced inside the existing Session write mutex immediately before the native write, so queued/fast-ACK requests cannot bypass400ms. Matching reports never cancel an in-flight write; finite request timers are isolated by monotonically increasing request IDs. App resume (or an already-dispatched tile click) requests one explicit retry after a transient ProtocolUnavailable state; passive listening never loops transport retries. No physical I/O timing claim follows from the unit tests.

## Apple proximity keys and case,0.2.0

The original codec uses [independent AAP key notes](https://github.com/stuffz/airpods/blob/main/docs/l2cap.md) and [observed BLE layouts](https://github.com/stuffz/airpods/blob/main/docs/ble.md). After fresh Apple identity, request `0400040030000500`; bounded type31 key records accept only exact16-byte IRK/AES entries. Temporary keys are copied then zeroized; ownership transfers to the current session, replaced/closed keys cleared. No persistent/shared key storage or key/identity/cipher diagnostic output.

Private-address matching follows Bluetooth SIG ah with a known test vector, without endian guessing. Known19-byte case advertisements have prefix071106 and one AES128/ECB block; validate decrypted2920 envelope, reserved zeros, percent/charging fields and increasing counter. FF is absent. Known27-byte pod advertisements require attributed address and expected decrypted envelope before exact percent replaces coarse nibbles. Unknown fields/layouts/replays are rejected. Counter rollback/reset requires a new session; replay cannot refresh timestamps.

This observational layout comes from another firmware, not an AirPods5 physical capture. AES block decoding does not authenticate the payload; strict shape guards reduce false acceptance but are not cryptographic integrity. Packet fixtures prove parser behavior only. A separate fresh case BLE reading survives a bud-link case-unavailable report; its own unavailable report withdraws it. No percent is invented to satisfy the UI.

## Sony native MDR/Tandem,0.2.0

Original Kotlin framing/negotiation follows [primary MDR docs](https://github.com/AndreasOlofsson/mdr-protocol), [V1 response report](https://github.com/marconvcm/sony-device-center/pull/36), [WF-XM4 subtype report](https://github.com/marconvcm/sony-device-center/issues/56), [ULT command documentation](https://github.com/Leonard013/sony-ult-ctl), [filtered captures](https://github.com/mos9527/SonyHeadphonesClient/tree/v1-compat/tests), and the [wire capability catalog](https://github.com/remon-nomer66/perch/blob/main/tools/protocol-source/functiontypes.json) with [provenance](https://github.com/remon-nomer66/perch/blob/main/tools/protocol-source/NOTICE.md). No companion-application implementation copied.

Native secure RFCOMM uses only an advertised V1 UUID96cc203e-5068-46ad-b32d-e316f5e069ba or V2 UUID956c7b26-d49a-4ba8-b03f-b17d393cb6e2. No fixed channel, audio-profile reconnect or Apple packet. Bounded2048-byte Tandem assembly validates escaping, type/sequence, big-endian length and checksum. Transport ACK advances framing sequence; only RET/NOTIFY listening settings confirm a mode. Retransmissions are ACKed but not reapplied.

Version, model and capability responses must be recognized. V1 and V2 IDs/commands stay separate: V1 opcode22 is not a battery query. Model prefix/service UUID alone never enables control. WF-XM4 uses its documented15 subtype; the captured6B capability family uses17; ULT has its documented special SET. Unknown schemas disable control. V1 ncType/asmType bytes are retained verbatim; their enum meanings are not claimed verified. Other operational fields are bounded. Adaptive Sound Control is not mapped to Apple mode4.

Capabilities gate battery queries. V1 handles single/dual/case; V2 advertised20/29/2A gates single or exact threshold-bearing dual/case schemas. Unequal public LinkBuds Clip captures corroborate component order; thresholds do not scale actual percentages, per [capture author's clarification](https://github.com/mos9527/SonyHeadphonesClient/issues/30). Unknown/invalid responses remain—; headphones expose one reading, TWS independent readings. Physical Sony qualification remains open.

Bootstrap holds the ordered request channel until initial battery requests finish, then signals Ready. Same-target UI retry is coalesced while the original SET/readback is in flight, preventing retry I/O timeout closing a healthy pending request. Different targets stay ordered; cancellation closes the socket before a queued stale write. Every actual mode write retains400ms spacing.
